# e2e fixtures

Two committed PDFs, each carrying the defect it is meant to trigger. Under
`AUDIT_ENGINE=langgraph` every verdict comes from what a vision model reads off the page, not
from the numbers typed into the upload form, so a fixture that does not carry its defect proves
nothing. Both are generated by `apps/api/scripts/generate-e2e-fixture.ts`:

```
bun run --filter '@starter/api' e2e:fixture
```

| Fixture                     | Uploaded by                          | Carries                                       |
| --------------------------- | ------------------------------------ | --------------------------------------------- |
| `sample-invoice.pdf`        | `audit-flow`, `review-flow`          | An arithmetic error the math check catches    |
| `clause-breach-invoice.pdf` | `contract-citation` (langgraph only) | A call-out charge no sum finds, only a clause |

## `sample-invoice.pdf`

**This must stay a real, renderable, one-page PDF. Do not replace it with a stub.**

It is a genuine Chromium print-to-PDF of a tax invoice, generated by
`apps/api/scripts/generate-e2e-fixture.ts` from the same `renderHtml` template the seeded
invoice PDFs use. Regenerate with:

```
bun run --filter '@starter/api' e2e:fixture
```

The bytes are committed rather than generated at test time, so the specs depend on no browser,
no database and no clock. Regenerating produces the same document but not the same bytes: the
Chromium writer stamps `/CreationDate` and `/ModDate`.

### Why it cannot be a stub

Under `AUDIT_ENGINE=langgraph` the engine downloads this PDF and a vision model reads it, so
the audit's verdicts come from what is printed on this page, not from the numbers typed into
the upload form. Before 2026-09-08 the fixture was a 69-byte object with no page tree and no
content. `file(1)` still called it "PDF document, version 1.4", so nothing caught it, and the
mock engine never opened the bytes. The moment a real engine read it, the Anthropic API
correctly rejected it (`The PDF specified was not valid`), extraction threw, the worker dropped
the job and both specs failed with no audit run to assert against.

### What is on the page, and why

Exactly one defect is planted, so a failure has one explanation:

| Property                  | Value                                             | Effect               |
| ------------------------- | ------------------------------------------------- | -------------------- |
| Lines sum to the subtotal | 4,000.00 + 440.00 = 4,440.00                      | correct              |
| Subtotal + GST vs total   | 4,440.00 + 444.00 = 4,884.00, printed as 5,328.00 | **wrong on purpose** |

`review-flow.spec.ts` needs an invoice that pauses for human review, and the honest way to get
one is an invoice that genuinely does not add up. The extraction prompt instructs the model to
transcribe what is printed even when the arithmetic looks wrong, so the mismatch survives
extraction and the math check fails on it.

### The defect fires, but nothing asserts on it

Do not read the table above as a guarantee. The `math = fail` verdict is real and observable in
`audit_runs`, but **no assertion in either spec depends on it**, so balancing the totals would
not turn either spec red.

The reason is the pause has a second, independent cause. The upload form fills no purchase
order, so `runPoMatchCheck` (`checks.ts:64-69`) returns `flag`, `rollUp` (`graph.ts:86-88`)
promotes any flag to the overall verdict, and the worker (`worker.ts:25-27`) pauses anything
that is not a clean `pass`. A balanced fixture still pauses, and `review-flow.spec.ts` still
passes.

So the arithmetic defect is deliberate and correct, and it is **not load-bearing**. A future
"tidy-up" that makes the totals add up would go uncaught by the suite. Change the numbers in the
generator, not the PDF, and if you change them, read this section first.

### What the four rendered check cards actually prove

Less than their count suggests, and this is a property of THIS fixture plus the upload form, not
of the engine. Vendors are listed ordered by name (`invoices/service.ts:181`) and both specs that
upload this file pick `getByRole('option').first()`, so the vendor is deterministically **Dodgy
Diggers Supplies Pty Ltd**, which the seed gives no contract at all.

| Check               | Verdict | What decided it                                                                                                                                      |
| ------------------- | ------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| `math`              | fail    | Real data: the numbers on this page                                                                                                                  |
| `po_match`          | flag    | The **absence** of data: no PO is linked                                                                                                             |
| `price_vs_contract` | pass    | Nothing: `worstOverage` (`checks.ts:118-138`) skips every line with no rate-card entry and returns null, so the check passes having compared nothing |
| `contract_terms`    | pass    | Nothing: retrieval returns zero clauses, so the check short-circuits without ever calling the model                                                  |

**These two specs prove the pipeline and the seam, not the checks.** Upload reaches the queue, the
queue reaches the engine, the engine's result reaches the database and the UI, and swapping
`AUDIT_ENGINE` changes none of that. Only one of the four verdicts is decided by real reference
data. The deterministic checks themselves are covered by the unit tier
(`engines/langgraph/checks.test.ts`); `contract_terms` is covered end to end by the second
fixture below.

## `clause-breach-invoice.pdf`

**Uploaded only by `contract-citation.spec.ts`, which runs only under `AUDIT_ENGINE=langgraph`.**
It exists to prove golden criterion 3: the contract-terms check retrieves clauses from the
generated MSA corpus through pgvector and cites the retrieved source in `sourceRef`.

### Why this invoice is arithmetically perfect

Lines sum to the subtotal, GST is exactly 10%, the total adds up, and the pump is billed at
Pilbara's contracted rate of $5,000.00 to the cent, so `math` and `price_vs_contract` both pass
it.

**`po_match` still flags, and no fixture can prevent that.** The upload form has no PO field, so
nothing uploaded through the UI carries a purchase order. This is therefore not an invoice whose
only defect is invisible to arithmetic; it is an invoice whose only defect _in the contract
dimension_ is.

| Line         | Description                                                 | Qty | Unit     | Total    |
| ------------ | ----------------------------------------------------------- | --- | -------- | -------- |
| `PUMP-100`   | Centrifugal slurry pump                                     | 1   | 5,000.00 | 5,000.00 |
| `CALLOUT-WE` | Weekend call-out loading, Saturday attendance outside hours | 1   | 850.00   | 850.00   |

Subtotal 5,850.00, GST 585.00, total 6,435.00.

### The breach, and why this vendor

Pilbara's **MSA-1000 §6** ("Hours of Work and Surcharges") forbids any surcharge, loading,
penalty or call-out fee for out-of-hours work "unless expressly approved in writing in advance".
`CALLOUT-WE` is on no rate card, so the price check has nothing to compare it against and skips
it: no sum on this page finds the call-out charge, only reading §6 does.

**Residual risk, stated plainly.** The missing purchase order is visible to the model as well as
to `po_match`, because `renderInvoice` (`contract-terms-agent.ts`) omits the PO line when there is
none. MSA §2 (payment terms) and §4 (purchase orders required) are therefore breachable on that
ground alone. If either reaches the retrieved top-4 and the model cites it, the spec goes green
without §6 having mattered. Every measured run so far has cited **§6**, and the spec deliberately
does not pin the clause number (see below), so this weakens what a green run proves rather than
making it wrong. The fixture is not changed to avoid it because no fixture can: the upload form
has no PO field.

The vendor must be one of the four the seed gives a contract (Pilbara Pumps, Kalgoorlie Valves,
Hedland Heavy Haulage, Goldfields Fasteners: 8 chunks each). The other two have zero chunks, and
a vendor with no clauses makes the check short-circuit to `pass` without ever calling retrieval,
which is exactly the vacuous state the spec asserts against. The breach mirrors the corpus's own
planted prose-only breach (seeded as INV-0021) rather than inventing one the generated MSAs
cannot express.

**The vendor name and ABN on this page must keep matching the seed**, because the spec selects
this vendor by name in the upload form.

### Which tier proves which half of criterion 3

The criterion has two halves and they are covered at different tiers. Do not tick the checkbox on
the e2e spec alone.

| Half                                                                                                               | Proven by                                  |
| ------------------------------------------------------------------------------------------------------------------ | ------------------------------------------ |
| Real clauses reach a real model, the verdict cites one, and the citation survives persistence and reaches the page | `contract-citation.spec.ts` (this fixture) |
| The clauses are selected **by embedding distance** and scoped to the vendor                                        | `retrieval.integration.test.ts`            |

The e2e spec cannot prove the pgvector half. Delete the `order by embedding <=> …` in
`retrieval.ts` and Pilbara's eight chunks still come back, the model still cites one, and the spec
stays green: the corpus is small enough that ordering does not change which chunks land in the
top-4.

### What it proves, and what it does not pin

Measured on this fixture: `contract_terms = fail`, `sourceRef = MSA-1000 §6`, with `math`,
`price_vs_contract` all passing and only `po_match` flagging (the upload form fills no PO).

The spec asserts the citation's SHAPE (`/^MSA-\d+ §\d+$/`), not the clause number. Which clause
the model cites is its judgement; the string itself is resolved from our own rows, because the
model returns a position in the list it was shown and `contract-terms-agent.ts` looks that
position up. So an invented reference has no way into the assertion, and a model that reasonably
cites §4 instead of §6 does not turn the suite red for no code reason.
